# Zero-Install Tunnel-as-a-Service: Design and Analysis of a Minimal Remote Access System for Personal Computing Devices

**mobile ai: Zero-Install Tunnel-as-a-Service for Minimal Remote Access to Personal Computing Devices — Design and Analysis**

> System version baseline: v1.0 (2026-09) · Intended audience: researchers in systems security, edge computing, and personal computing
> Keywords: tunnel-as-a-service; zero-install remote access; capability security; URL-as-credential; zero-knowledge control plane

---

## Abstract

**Abstract.** Remote access to personal computing devices has been split between two camps: client-heavy approaches such as Tailscale and ZeroTier, which require installing software on *both* ends to form a virtual private network; and one-sided tunneling tools such as ngrok or Cloudflare quick tunnels, which require no client on the consumer device but provide little in identity management and revocation. We present **mobile ai**, a *zero-install tunnel-as-a-service*: the user runs a single `curl | bash` command on their home computer, establishing an outbound Cloudflare Tunnel that yields a dedicated URL of the form `https://<random-subdomain>.newapi.email`; a phone browser reaches local services on the home machine (by default, the DSH Web GUI) with no mobile app and no public IP or port forwarding. Version 1.0 further simplifies the identity model: the one-time authentication code is eliminated, with a machine code serving as the sole identifier for automatic no-code registration; a local multiplexer (mux) supports mounting multiple tool services on a single tunnel; and three-platform one-click install scripts are provided. The system is strictly layered: the control plane (Node.js + SQLite) handles only machine-code registration, binding management, heartbeat liveness, and online-time tracking; the data plane lives entirely on the user's machine, with Cloudflare edge performing TLS termination and forwarding only — the platform never decrypts or proxies business traffic. The security model is capability-based: a random subdomain URL *is* the access credential, and URL rotation equals revocation. We formalize this model (zero-retention and revocation semantics), give conservative capacity estimates from Cloudflare's public free-plan limits, and evaluate each design decision via a trade-off table. The system is in production (v1.0).

## 1. Introduction

"You are on the road, yet your home computer sits idle" is a plain and pervasive problem of the personal computing era. As AI coding agents (such as DeepSeek Harness, Codex) and self-hosted web applications increasingly depend on long-running local compute, users want to drive the complete toolchain of their home computer directly from a phone browser — not by relaying screen pixels as in remote desktop, but by reaching the local HTTP services themselves.

Existing solutions are split into three categories:

1. **End-to-end client VPNs (Tailscale, ZeroTier)** [1][2]. Both ends must install and log into the same virtual network; deployment friction is high, and a perpetually running VPN plane is introduced — for an individual user this amounts to "reconfiguring the entire network just to reach one machine."
2. **Generic tunneling tools (ngrok, cloudflared quick tunnel)** [3][4]. Only one end needs installation, but ngrok's free tunnel URLs are short and require account binding; the random URL generated by cloudflared quick tunnel (`--url https://trycloudflare.com`) carries no identity management whatsoever — once leaked, access is lost and cannot be revoked.
3. **SaaS hosting (various cloud IDEs, for example)**. Data and compute move to the cloud, violating the privacy demand that "everything stays on my own machine."

The design goal of mobile ai v1.0 is to simultaneously satisfy five seemingly conflicting properties: **(a)** zero installation on the user side (one command + one browser page); **(b)** zero application on the consumer end (the phone uses only its system browser); **(c)** zero business-traffic contact on the platform side (the control plane neither decrypts nor retains); **(d)** revocable access credentials; **(e)** no-code automatic authentication (machine code = identity, no one-time codes). These five properties have never co-occurred in existing solutions: client VPNs sacrifice (a) and (b); tunneling tools sacrifice (d)(e) (or offer only platform-side, non-self-service revocation); SaaS hosting sacrifices (c). This paper argues that all five can coexist, provided "identity and revocation" is peeled off the data path into a separate control plane, and multiplexing is pushed down to the user's local machine. The contributions of this paper:

- **Architecture**: a strictly layered design separating control plane from data plane, with a local lightweight mux achieving "one tunnel, many tools"; v1.0 introduces no-code automatic registration (machine code = identity) and a tool preset system;
- **Security model**: formalizing the semantics of "URL-as-credential" and "rotation = revocation" in the capability-based security paradigm [5], together with a zero-retention argument;
- **Engineering analysis**: conservative capacity estimates based on public free-tier quotas, and a trade-off evaluation table over the design decisions (including v1.0 no-code auth vs v0.5 one-time code comparison).

## 2. Related Work

### 2.1 End-to-End Client VPNs
Tailscale [1], built on WireGuard, provides end-to-end encrypted peer connections via "mesh over DERP," emphasizing zero configuration and device identity; ZeroTier [2] offers virtual-LAN semantics. Both require **installing a client on both ends and joining the same named network**. Their strength is device identity with mDNS discovery; their cost is a resident agent on every endpoint. mobile ai differentiates itself by **zero installation on the consumer end**: the phone is merely an HTTPS client and joins no virtual network at all.

### 2.2 Tunneling and Port-Exposure Tools
ngrok [3] offers tunnels with identity and auditing, but the client must register and bind to an account, and URL lifecycles are controlled by the platform; Cloudflare Tunnel (cloudflared) [4] supports both named tunnels and token mode, in which the latter has **no local `config.yml` at all — ingress is fully controlled by the control plane via API** — this is precisely what makes mobile ai's "one tunnel, many ingresses" feasible. Cloudflare quick tunnels provide no persistent identity and no revocation; on top of them, mobile ai completes **one-time codes + machine binding + rotation-based revocation**.

### 2.3 Credential and Access-Control Theory
- **Capability security** [5][6]: an unforgeable reference (token) *is itself* the authorization — holding it grants access, and it is transferable; revocation works by **invalidating the reference or making it unresolvable**. The random-subdomain URL of mobile ai is exactly such a high-entropy, unguessable capability reference; rotating the URL equates to invalidating the old capability.
- **Bell-LaPadula and least privilege** [7]: emphasize "no read up / no write down" constraints on access. mobile ai follows least privilege [8]: the control plane holds only orders, codes, and binding state — **it possesses no capability to access any business data**.
- **Let's Encrypt and ACME** [9]: automated certificate issuance underpins the ubiquity of "edge TLS"; mobile ai reuses the certificates Cloudflare issues automatically for each subdomain, requiring no user-owned domain or certificate.

## 3. System Architecture

### 3.1 Layered Overview
mobile ai is strictly divided into three layers; **the control plane and the data plane are fully isolated in code, deployment, and trust boundary**.

```
┌───────────────┐  HTTPS (TLS)   ┌─────────────────────────────────────┐
│ Phone browser │ ─────────────▶ │   Cloudflare Edge (TLS termination  │
│ (zero app)    │                │              + forwarding)          │
└───────────────┘  HTTPS        └──────────────┬──────────────────────┘
┌───────────────┐  /api/*           outbound tunnel (cloudflared,
│ Portal /me    │ ──magic link──▶   initiated by user's machine)
│ (control-plane│                  ▼
│      entry)   │          ┌─────────────────────────────────────┐
└───────────────┘           │  User's home PC (data plane,       │
      ▲                     ├─────────────────────────────────────┤
      │ magic-link email    │  cloudflared ─▶ mux :5380           │
      ▼                     │   /t/<name> ─▶ 127.0.0.1:<port>     │
┌───────────────┐           │   default tool DSH @ 127.0.0.1:3080  │
│ Workers + D1  │           └─────────────────────────────────────┘
│ (control plane:│   management plane only, no business traffic
│  codes/binding │
│ /heartbeat/rot)│
└───────────────┘
```

**Key fact**: Cloudflare Tunnel ingress **matches on hostname only — it performs no path/query routing**. Therefore "many tools" is realized by a local mux on the user's machine (the `:5380` segment, path `/t/<name>` → `127.0.0.1:<port>`, including WebSocket upgrade passthrough); the tunnel ingress is always a single rule `sub.newapi.email → http://127.0.0.1:<muxPort>`.

### 3.2 Control Plane
v1.0 is deployed on Node.js + SQLite (local or VPS), its responsibilities deliberately narrowed to five:

| Function | Mechanism (v1.0) |
|---|---|
| **No-code auto-registration** (L1) | machine code + platform as sole identity; activate is idempotent — reactivating the same machine returns existing credentials, no one-time code required |
| **Machine binding + heartbeat** (T1) | single-device policy: one authorized machine; 30s heartbeat, tracks `cumulative_online_ms` (5-min delta cap) and `first_seen`/`last_offline_at` lifecycle |
| **Tool management** (T2) | each binding can mount multiple `{name, port}` tools; visible in admin dashboard, synced to local mux routing table |
| **Referral attribution** (X9) | optional `ref` parameter in activate records referrer machine code; admin stats aggregate Top N |
| **URL rotation** | the entire tunnel gets a new random subdomain; the old URL dies instantly, the new one takes effect within seconds; machine code unchanged, client needs no re-run |

The control plane **proxies no business traffic at all** — this is the foundation of the zero-retention argument (§4.3).

> **v0.5 → v1.0 evolution**: The v0.5 control plane was deployed on Cloudflare Workers + D1 (edge computing), using magic-link email login and one-time authentication codes (`MAI-XXXXXX`, 6 digits). v1.0 migrates the control plane to Node.js + SQLite (reducing cold-start latency, simplifying deployment), eliminates the one-time code mechanism, and uses machine code directly as identity for no-code automatic registration. Security semantics are unchanged (URL-as-credential + machine binding), but user friction is further reduced: from "request code → receive email → enter code to activate" simplified to "one command and you're done."

### 3.3 Data Plane and Local Mux
- **cloudflared (token mode)**: `tunnel --token <T> run`; ingress is written by the control plane via the CF API; no local `config.yml`.
- **mux**: a fixed-port HTTP reverse proxy inside the daemon; routing table (local memory + `state.json`) as follows:
  - `GET/POST /` → default tool (DSH :3080)
  - `/t/<name>/…` → `tools[name].addr` (equivalent to the query form `?tool=<name>`; mux normalizes it into a path)
  - `/t/<name>/ws`, upgrade → WebSocket passthrough (including DSH Origin stripping)
  - unknown name → `404 {error:'tool not found', tools:[…]}` (troubleshooting-friendly)
- **Many tools at zero cost**: adding a tool only edits the local mux routing table — **no second tunnel, no extra CNAME**; one URL rotation covers all tools.

### 3.4 TLS Termination Location and End-to-End Encryption
TLS is **terminated at the Cloudflare edge**, then forwarded over an encrypted tunnel channel between Cloudflare and the user's machine to the local mux. For business traffic, the platform **does not decrypt, cache, or retain**; the edge only performs TLS termination and byte forwarding. This differs from VPN approaches that "terminate on the user's machine, end-to-end throughout" — mobile ai trusts the Cloudflare edge as an **honest forwarder**, trading that assumption for zero consumer installation and a minimal platform.

## 4. Security Model

### 4.1 URL-as-Capability: The URL Is the Capability Reference
The random subdomain (high-entropy, non-enumerable) is **the sole access credential**. This matches the capability-security paradigm exactly [5][6]: an unforgeable reference is itself authorization; holding it grants access. Its strength depends on the subdomain's entropy and unguessability (a random subdomain under `newapi.email`; an attacker cannot enumerate valid values). **Revocation semantics**: URL rotation = generating a new capability reference and making the old one unresolvable (DNS/ingress pointer changes) — equivalent to capability revocation, a property traditional session tokens lack (they cannot be actively invalidated).

### 4.2 No-Code Auto-Registration and Machine Binding (v1.0)
- **Identity = machine code**: format `MAI-XXXXX-XXXXX`, generated by the client on first launch and persisted in `~/.mobileai/state.json`. The activate request carries machine code + platform; the control plane idempotently registers or returns existing bindings — **no one-time code, email, or manual confirmation required**.
- **Idempotent semantics**: same machine code reactivating → returns existing tunnelToken + URL (no new tunnel created); different machine code → creates a new binding.
- **Machine binding**: the single-device policy locks onto "your computer" (one authorized machine); a phone or tablet opening the same URL simultaneously is a matter of **client count** and is unrestricted. A heartbeat from the wrong machine auto-revokes ("wrong machine, instant kill").
- **Defense in depth**: URL capability + machine-code binding + heartbeat revocation form three layers; a flaw in any single layer is backstopped by the others.
- **v0.5 comparison**: The one-time code (`MAI-XXXXXX`) was removed in v1.0. Security analysis: the threat model for a code is "email leakage → someone else activates on your behalf," but the machine code itself already encodes a hardware fingerprint (platform + hostname hash), equivalent to compressing the "code leakage window" to zero — identity *is* the machine, no intermediate credential needed.

### 4.3 Zero-Retention Argument
**Claim**: under steady-state operation, the mobile ai control plane holds no user business-traffic content, decrypts none of it, and retains none of it.
**Key points**: (1) the data-plane path is `phone ⇄ Cloudflare Edge ⇄ cloudflared (user's machine)`; the control-plane Workers are not on that path; (2) ingress contains only hostname→local-address mappings, with no traffic-content fields; (3) the `bindings` table in D1 stores only orders, code state, machine-code hashes, and subdomains — **no request/response bodies**. Hence the platform is zero-knowledge with respect to business traffic (a zero-knowledge control plane). Boundary statement: whatever services the user exposes is the user's responsibility; the platform performs no content moderation (see `SECURITY.md` for known boundaries).

### 4.4 Threat Model and Trust Assumptions
- **Honest forwarder**: the Cloudflare edge is assumed not to actively decrypt or retain business traffic (§3.4).
- **Machine code is practical-grade**: it provides deterrence + heartbeat revocation, not DRM; hardware changes require manual re-binding (`SECURITY.md`).
- **URL leakage**: equivalent to a password leak; mitigation = one-click rotation + (optionally) Cloudflare Access email verification as a second layer.

## 5. Capacity Analysis

Full engineering detail in `docs/CAPACITY.md` (updated 2026-09). The following are conservative estimates based on **Cloudflare's public free-plan limits**. Assumptions: single user, default DSH (:3080) plus 1–2 additional tools, interactive usage.

| Resource | Free-plan public limit (conservative value) | mobile ai consumption point | Estimate and conclusion |
|---|---|---|---|
| **Workers** (control plane) | ~100k req/day, ≤10ms CPU per request (free tier) | magic-link / code redemption / heartbeat / rotation — **low-frequency, event-driven** | a single user issues tens to hundreds of control requests per day ≪ 100k; the bottleneck only appears in multi-tenant aggregation |
| **D1** (control-plane storage) | 5 GB / database | `bindings`, code state, email-queue metadata — **no traffic content** (§4.3) | KB–MB scale per user; 5 GB is extremely generous; multi-tenant growth scales linearly with binding count |
| **Cloudflare Tunnel** (data plane) | no official concurrency cap; bandwidth constrained by the edge network | all business traffic forwarded via the tunnel (after TLS termination) | **not a quota bottleneck**; constrained by user uplink bandwidth and CF edge forwarding rate — interactive DSH (text/WS) stays far below any hard cap |

**Conservative conclusions and assumptions**:
1. **Control-plane quotas do not constrain a single user.** The ~100k req/day Workers figure targets **platform-wide aggregation**; one user's control events (heartbeat every 30 min ≈ 48/day + occasional logins/rotations) are a negligible fraction. What truly needs monitoring is the aggregated Workers request count and D1 write rate **under multi-tenancy**.
2. **The data plane is not hard-capped by free-tier quotas**, but is bounded by physical bandwidth: a text/JSON/WebSocket-heavy workload like DSH uses very little uplink; large-file downloads are limited by the user's **home uplink bandwidth** (typically 20–100 Mbps), not by CF quotas.
3. **Assumptions**: (a) the user is interactive, not high-throughput file synchronization; (b) free-plan limits follow Cloudflare's official documentation and may change over time — this paper takes conservative values; (c) WS/SSE long-lived connections consume **concurrent connection count**, not request quota, and CF Tunnel has no official concurrency cap, so it is excluded from the estimate.
4. **Single point of failure**: mux is a local single point (a crash = all tools unavailable, though the tunnel survives and heartbeats continue); recovery is via daemon KeepAlive restart — an availability issue, not a capacity one.

**Resource comparison with VPN approaches**: Tailscale/ZeroTier maintain a resident agent at each end (WireGuard kernel- or user-space forwarding, DERP relay), whose resource overhead grows with "device count × active connections"; mobile ai's data-plane cost is concentrated in **a single user machine running cloudflared + mux**, while the consumer end (phone browser) consumes only ordinary HTTPS connection resources. mobile ai's capacity bottleneck is therefore **one tunnel per user + control-plane event rate**, not a network-wide device matrix — a better-fitting resource model for the "individual accessing one's own single machine" scenario.

> Recommendation: after launch, continuously observe control-plane latency and tunnel-reconnect delay with `dns-probe` (US runner E2E) + `/mai/healthz`, as an empirical calibration of the capacity assumptions.

## 6. Evaluation: Design-Decision Trade-offs

| # | Decision point | Alternatives | Adopted | Benefit / cost (trade-off) |
|---|---|---|---|---|
| D1 | Identity authentication method (v0.5→v1.0) | A v0.5 one-time code / B magic-link + long-lived token / C **v1.0 machine code = identity (no-code)** | **C** | ✅ zero friction, no email dependency, idempotent; ⚠️ machine code leakage = someone else can activate on your behalf (mitigation: machine binding + heartbeat revocation) |
| D2 | Multi-tool topology | a one tunnel per service / b edge Worker path routing / c **local mux** | **c + `?tool=`** | ✅ URL rotation drops from N×2 API calls → 1; start/stop is second-level and reversible; WS/SSE verified; ⚠️ mux single point |
| D3 | URL form | `?tool=` query vs subdomain prefix | **`?tool=`** | ✅ zero DNS, no new CNAME; rotation = swap subdomain; ⚠️ URL slightly longer (acceptable) |
| D4 | TLS termination location | edge termination vs user-machine end-to-end | **edge termination** | ✅ zero consumer installation, minimal platform; ⚠️ introduces the "trust CF edge as honest forwarder" assumption |
| D5 | Revocation mechanism | session token (cannot be actively invalidated) vs **URL rotation = capability invalidation** | **URL rotation** | ✅ clear active-revocation semantics, user self-service; ⚠️ requires client not to re-run (satisfied: machine code unchanged) |
| D6 | Number of auth layers | URL only vs **URL + (optional) CF Access** | **layered, Access can be disabled** | ✅ defense in depth; ⚠️ Access email verification adds a step for first phone access (can be disabled) |
| D7 | Machine-binding strength | DRM-grade vs **practical grade (deterrence + heartbeat revocation)** | **practical grade** | ✅ simple implementation, controllable false positives; ⚠️ hardware changes need manual re-binding (not DRM) |
| D8 | Consumer-end form factor | native app vs **system browser** | **browser** | ✅ zero installation, cross-platform; ⚠️ constrained by browser capabilities (no local notifications, etc.) |

**Evaluation conclusion**: every decision makes an explicit trade-off between "user friction" and "security strength / platform complexity," and **every security action in every layer is designed to be cheap and repeatable** (rotation = one click, start/stop = seconds), because "the cheaper a security action is, the more users will actually use it." Note in particular the coupling between D2 and D4: choosing a local mux (D2) lets one URL rotation cover all tools, while edge TLS termination (D4) means that rotation only touches DNS/ingress — never the data path. The two decisions amplify each other, jointly driving the cost of "revocation" to its minimum. Conversely, with one tunnel per service (D2-a), rotation cost grows linearly with tool count; the security action becomes expensive and users avoid it, weakening overall security instead. This shows that **revocation cost is a first-class design variable of the security model**, not an after-the-fact patch.

## 7. Discussion and Limitations

1. **Trust boundaries are shifted, not eliminated**: mobile ai trades the friction of "clients on both ends" for "trusting the Cloudflare edge as an honest forwarder." For highly sensitive scenarios (medical, financial), add a CF Access second layer or revert to end-to-end VPN.
2. **Machine code is not DRM**: practical-grade binding can be bypassed by cloning a VM fingerprint, relying on heartbeat revocation as backstop; this is deliberate — the false positives of DRM-grade binding (replacing a disk/motherboard) are unacceptable to individual users.
3. **Granularity of the single-device policy**: it locks onto "one authorized machine," not "one session"; multiple consumer devices sharing the same URL are unrestricted. Per-consumer authorization would require a consumer-side identity (deliberately omitted today to preserve zero installation).
4. **Capacity is estimated**: §5 rests on conservative assumptions from public free-tier quotas, without measured P99; calibration with `dns-probe` and production telemetry is needed.
5. **Mux single point**: a local mux failure makes all tools unavailable (the tunnel survives); recovery relies on KeepAlive; multi-tenant SaaS deployment would need health checks and automatic degradation.
6. **URL entropy assumption**: revocation semantics depend on subdomain non-enumerability; if predictable naming is introduced in the future (e.g., user-defined prefixes), capability strength must be re-evaluated. The current random subdomain is generated by the control plane at activation; its entropy should make brute-force enumeration infeasible — this paper treats it as a security axiom rather than an empirically measured conclusion.
7. **Single-user assumption**: the paper's capacity and binding analysis baselines on "one account, one authorized machine"; quota governance under multi-tenant aggregation (point 1 of §5) and per-consumer authorization (limitation 3) are dimensions that must be completed for SaaS-ification, and lie beyond this paper's scope.

## 8. Conclusion

mobile ai v1.0 demonstrates that "zero installation + zero consumer app + zero platform business-traffic contact + no-code automatic authentication" can coexist: through **strict control/data-plane layering**, a **local mux realizing many tools over one tunnel**, and a security model centered on the **capability paradigm** (URL-as-credential, rotation = revocation, machine-code binding + heartbeat revocation defense in depth). The system is in production at v1.0, supporting six core features: L1 (no-code auth), L2 (local mux multi-tool), T1 (online-time tracking), T2 (tool presets and admin UX), A1 (aliasing), and X9 (referral attribution). Our analysis shows that remote access to personal computing devices need not be a binary choice between "client friction" and "revocable security credentials" — the key is to place **identity management and revocation semantics** in the control plane, while keeping **data and compute on the user's machine**. Future work: an optional consumer-side identity layer (without breaking zero installation), measured capacity calibration, multi-tenant aggregated quota governance, and standardized integration of CF Access as a second authentication layer.
